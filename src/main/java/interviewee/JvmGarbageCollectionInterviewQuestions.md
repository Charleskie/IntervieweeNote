# JVM 垃圾回收机制面试题清单

> 复习重点：GC 面试通常不是只问概念，而是追问“对象什么时候回收、为什么 Full GC、怎么看 GC 日志、如何调优、线上 OOM 怎么处理”。

## 1. JVM 内存区域和 GC 有什么关系？

- [ ] 哪些区域会发生垃圾回收？
  答案：GC 主要发生在堆和方法区/元空间。堆存放对象实例，是 GC 的主战场；元空间存类元信息，也可能因类加载过多触发回收。虚拟机栈、本地方法栈、程序计数器随线程生命周期释放，不是 GC 重点。 直接内存不在堆内，但也可能造成 OOM，需要关注 `MaxDirectMemorySize`。

## 2. 如何判断对象是否存活？

- [ ] 引用计数和可达性分析有什么区别？
  答案：引用计数给对象维护引用数量，计数为 0 可回收，但无法解决循环引用。Java 主流 JVM 使用可达性分析，从 GC Roots 出发，不可达对象才可回收。 GC Roots 包括栈帧局部变量、静态字段、常量、JNI 引用、同步锁持有对象等。 Java 主流 JVM 使用可达性分析。从 GC Roots 出发，沿引用链向下遍历，能到达的对象认为存活，不能到达的对象才可能被回收。引用计数法虽然简单，但无法处理循环引用，所以不是 HotSpot 判断对象存活的主流方式。 常见 GC Roots 包括：虚拟机栈中局部变量表引用的对象；方法区/元空间中类静态字段引用的对象；运行时常量池引用的对象；本地方法栈 JNI 引用的对象；被 synchronized 锁持有的对象；JVM 内部引用对象，例如系统类加载器、异常对象等。 如果这两个对象只是在彼此之间形成循环，但从 GC Roots 不可达，就可以被回收。可达性分析解决的正是引用计数难以解决的循环引用问题。 不一定。对象从不可达到真正回收，中间还会经历标记、清理、可能的 finalization 等过程。并发收集器还可能有浮动垃圾，本轮标记结束后新产生的垃圾可能要等下一轮 GC 才回收。不要把“不可达”和“马上释放内存”画等号。

## 3. 对象一定不可达就会马上回收吗？

- [ ] `finalize` 对回收有什么影响？
  答案：不可达对象会经历标记过程。如果对象重写了 `finalize` 且未执行过，可能进入 F-Queue 等待执行，有一次自救机会。但 `finalize` 不可靠、性能差，已不推荐使用。 不要依赖 `finalize` 做资源释放，应该用 `try-with-resources` 或显式 close。

## 4. Java 引用类型有哪些？

- [ ] 强引用、软引用、弱引用、虚引用有什么区别？
  答案：强引用只要存在就不回收；软引用在内存不足时回收，常用于缓存；弱引用下一次 GC 就可能回收，常用于 ThreadLocal key；虚引用无法获取对象，主要配合 ReferenceQueue 追踪回收。 软引用缓存不等于可靠缓存，生产更常用 Caffeine/Redis 等明确策略。 强引用是最普通的引用，只要强引用存在，对象就不会被回收。软引用在内存不足时可能被回收，过去常被用作缓存。弱引用只要发生 GC 就可能被回收，常见于 `WeakHashMap`、ThreadLocal key 等场景。虚引用不能通过 `get()` 获取对象，主要配合 ReferenceQueue 感知对象回收，常用于堆外内存清理等底层场景。 生产中不要把软引用当成可靠缓存。软引用回收时机和 GC 策略有关，命中率不可控。业务缓存更推荐 Caffeine、Guava Cache、Redis 这类明确容量、TTL 和淘汰策略的方案。 ThreadLocalMap 的 key 是弱引用，ThreadLocal 对象本身如果没有强引用，key 可能被 GC 回收，但 value 仍然被 Entry 引用。如果线程长期存活，比如线程池线程，value 可能一直留在 ThreadLocalMap 中，造成泄漏。所以使用 ThreadLocal 后要在 finally 中 `remove()`。 弱引用对象只要没有强引用链可达，在下一次 GC 时会被清理。但是否马上发生 GC、何时处理 ReferenceQueue，都由 JVM 决定。面试中要区分“回收条件”和“回收时间”。

## 5. 常见 GC 算法有哪些？

- [ ] 标记清除、复制、标记整理分别是什么？
  答案：标记清除先标记存活对象再清理垃圾，简单但产生碎片；复制算法把存活对象复制到另一块空间，无碎片但浪费空间；标记整理把存活对象向一端移动，减少碎片但移动成本高。 新生代对象大多朝生夕死，适合复制算法；老年代存活率高，更常用标记清除/整理。 标记清除先标记存活对象，再清理未标记对象，优点是简单，缺点是容易产生内存碎片。复制算法把存活对象复制到另一块空间，清理原空间，优点是没有碎片，适合存活对象少的区域，缺点是需要额外空间。标记整理会标记存活对象，然后把存活对象向一端移动，减少碎片，缺点是移动对象成本高。 分代收集就是基于对象生命周期差异选择算法。年轻代大多数对象朝生夕死，适合复制算法；老年代对象存活率高，如果还用复制算法成本太大，所以常用标记清除、标记整理或 Region 化回收。 两个 Survivor 是复制算法的实现基础。Minor GC 时，Eden 和当前 From Survivor 中存活对象复制到 To Survivor，然后 From/To 角色交换。这样每次只使用一个 Survivor 作为来源，一个作为目标，保证整理后的对象连续，减少碎片。 对象每经过一次 Minor GC 并在 Survivor 中存活，年龄通常加 1。达到 `MaxTenuringThreshold` 后晋升老年代。但 JVM 还有动态年龄判断：如果某个年龄及以上对象总大小超过 Survivor 的一定比例，这些对象可能提前晋升，避免 Survivor 放不下。

## 6. 分代收集理论是什么？

- [ ] 为什么 JVM 要分新生代和老年代？
  答案：大部分对象生命周期很短，少部分对象存活很久。分代后，新生代用较高频率回收短命对象，老年代低频回收长寿对象，可以提升整体效率。 分代是假设，不同业务如缓存型应用可能有大量长寿对象，需要结合场景调优。

## 7. 新生代 Eden、Survivor 是怎么工作的？

- [ ] 对象在新生代如何流转？
  答案：对象通常先分配在 Eden；Minor GC 时 Eden 和一个 Survivor 中存活对象复制到另一个 Survivor，年龄加 1；达到晋升阈值或 Survivor 放不下时进入老年代。 Survivor 默认比例常见是 Eden:S0:S1 = 8:1:1，但可调。 对象通常先在 Eden 区分配。为了减少多线程分配竞争，JVM 会给线程分配 TLAB，线程优先在自己的 TLAB 中快速分配；如果对象太大或 TLAB 放不下，就走慢路径在 Eden 中分配。Eden 空间不足时触发 Minor GC，存活对象会被复制到 Survivor 区，年龄加 1。对象多次 Minor GC 后仍然存活，或者 Survivor 放不下，或者对象本身很大，就可能晋升到老年代。老年代空间不足、元空间压力、显式 `System.gc()`、晋升担保失败等都可能触发更重的 GC。 面试时可以把对象生命周期讲成：分配、年轻代回收、年龄增长、晋升、老年代回收、不可达后清理。这样比只说 Eden/Survivor 更完整。 从 JVM 规范和普通理解看，对象在堆上分配。但 JIT 优化可能通过逃逸分析做标量替换或栈上分配的效果。如果对象没有逃出方法，JVM 可能不真的分配完整对象，而是把字段拆成局部变量，减少堆分配和 GC 压力。面试中可以说“语义上对象属于堆，但运行时可能被 JIT 优化掉”。 大对象进入 Eden 后如果复制到 Survivor 成本高，或者 Survivor 容纳不下，会直接进入老年代。这样可以减少年轻代复制成本，但如果频繁创建大对象，会快速占满老年代，触发 Full GC。典型场景有大数组、大字符串、大批量查询结果。

## 8. Minor GC、Major GC、Full GC 有什么区别？

- [ ] 哪类 GC 对系统影响最大？
  答案：Minor GC 回收新生代，频率高但通常较快；Major GC 常指老年代 GC；Full GC 回收整个堆和方法区相关区域，停顿通常最长，对系统影响最大。 术语在不同收集器和日志中略有差异，实际要结合 GC 日志判断。 Minor GC 通常指年轻代回收，频率高但停顿相对短。Major GC 有时指老年代回收，但不同资料和收集器语义不完全一致。Full GC 通常指覆盖整个堆，甚至包括元空间相关清理，停顿最重。G1 中常见 Young GC 回收年轻代 Region，Mixed GC 会同时回收年轻代和一部分老年代 Region。 面试时最好避免死抠术语，可以说：不同 JVM 和收集器日志命名不同，实际分析要以 GC 日志里回收区域、触发原因和停顿时间为准。 通常比 Young GC 慢，因为扫描和整理范围更大，停顿更长。但具体还要看堆大小、存活对象数量、收集器和硬件。一个小堆 Full GC 可能几十毫秒，一个大堆且对象存活率高的 Full GC 可能数秒甚至更久。调优时关注 P95/P99 停顿和频率，而不是只看一次。 `System.gc()` 只是建议 JVM 进行 GC，但很多 HotSpot 配置下会触发 Full GC，造成明显停顿。生产中通常不建议业务代码主动调用，可以通过 `-XX:+DisableExplicitGC` 禁用显式 GC 请求，或者谨慎评估第三方库行为。

## 9. 什么情况下对象会晋升到老年代？

- [ ] 老年代对象来源有哪些？
  答案：对象年龄达到阈值、动态年龄判断、Survivor 空间不足、大对象直接进入老年代、Minor GC 后担保分配失败等都可能导致晋升。 晋升过快会导致老年代压力增大，进而触发 Full GC。

## 10. TLAB 是什么？

- [ ] 为什么需要 TLAB？
  答案：TLAB 是线程本地分配缓冲区，每个线程在 Eden 中预留一小块空间，避免多线程对象分配时频繁竞争，提高分配效率。 对象太大或 TLAB 放不下时会走慢路径分配。

## 11. 什么是 Stop-The-World？

- [ ] 为什么 GC 会 STW？
  答案：STW 是 GC 时暂停用户线程，保证对象引用关系在某些阶段稳定。即使是并发收集器，也通常存在初始标记、最终标记等短暂停顿阶段。 低延迟收集器的核心目标是缩短 STW，而不是完全没有 GC 工作。

## 12. Serial、Parallel、CMS、G1 怎么理解？

- [ ] 常见垃圾收集器各自特点是什么？
  答案：Serial 单线程，适合小堆客户端；Parallel 吞吐优先，适合后台计算；CMS 低停顿并发标记清除，但有碎片和浮动垃圾；G1 面向服务端大堆，按 Region 回收，兼顾停顿和吞吐。 JDK 9 后 G1 成为默认收集器之一，CMS 已在后续版本中被移除。

## 13. CMS 的执行流程是什么？

- [ ] CMS 为什么会产生碎片？
  答案：CMS 主要流程是初始标记、并发标记、重新标记、并发清除。它使用标记清除算法，不移动对象，所以容易产生内存碎片。 CMS 并发阶段用户线程仍运行，会产生浮动垃圾，可能出现 concurrent mode failure。 CMS 是以低停顿为目标的老年代收集器，主要流程是初始标记、并发标记、重新标记、并发清除。初始标记和重新标记需要 STW，并发标记和并发清除可以和用户线程同时执行，所以相比传统老年代收集器停顿更短。 CMS 的缺点也明显。它使用标记清除，不整理对象，容易产生内存碎片；并发阶段用户线程还在运行，会产生浮动垃圾；如果老年代预留空间不足，可能出现 concurrent mode failure，退化为更重的 Full GC；CMS 对 CPU 资源也比较敏感。后来 G1 通过 Region 化、可预测停顿、Mixed GC 等方式更适合大堆服务端场景，所以逐步取代 CMS。 并发标记过程中，用户线程仍在创建和修改对象。标记开始后新产生、或标记过程中变成垃圾的对象，本轮 CMS 未必能清理，只能留到下一轮，这部分就是浮动垃圾。因此 CMS 需要预留足够老年代空间，否则并发清理还没结束老年代就满了。 CMS 使用标记清除，只把垃圾对象位置标为空闲，不移动存活对象。久而久之，老年代会出现很多不连续小块空间。总空闲空间可能够，但找不到连续空间分配大对象，就可能触发 Full GC 做压缩整理。

## 14. G1 的核心思想是什么？

- [ ] G1 为什么适合大堆？
  答案：G1 把堆划分为多个 Region，不再固定物理新生代/老年代区域。它根据每个 Region 的垃圾比例和回收成本，优先回收收益高的 Region，并通过停顿预测控制 STW 时间。 G1 的 Humongous 对象会占用连续 Region，处理不好也可能导致 Full GC。 G1 把堆划分成多个大小相等的 Region，每个 Region 可以扮演 Eden、Survivor、Old 或 Humongous。G1 不再固定物理上的年轻代和老年代，而是按 Region 管理。它会估算每个 Region 的回收收益和成本，优先回收垃圾最多、收益最高的 Region，所以叫 Garbage First。 G1 的目标是可预测停顿。用户可以设置 `MaxGCPauseMillis`，G1 会尽量选择合适数量的 Region 组成 Collection Set，在目标停顿时间内完成回收。它通过 Remembered Set 记录跨 Region 引用，避免每次回收某些 Region 时扫描全堆。 当堆占用达到 `InitiatingHeapOccupancyPercent` 等阈值后，G1 触发并发标记，识别老年代 Region 的存活情况。标记完成后，后续若干次 GC 会在回收年轻代的同时，选择一部分垃圾比例高的老年代 Region 一起回收，这就是 Mixed GC。它不是一次性回收全部老年代，而是分批回收，降低单次停顿。 G1 中超过 Region 一半大小的对象会被视为 Humongous，需要占用一个或多个连续 Region。大对象频繁分配会造成连续 Region 压力和碎片问题，可能触发并发标记甚至 Full GC。常见治理方式是减少大对象创建、分批处理、流式处理、调整 Region 大小或优化数据结构。

## 15. G1 的回收流程是什么？

- [ ] G1 Young GC 和 Mixed GC 有什么区别？
  答案：Young GC 主要回收新生代 Region；当老年代占用达到阈值后触发并发标记，之后进行 Mixed GC，同时回收新生代和部分老年代 Region。 G1 会维护 Remembered Set 记录跨 Region 引用，避免全堆扫描。

## 16. ZGC 和 Shenandoah 的特点是什么？

- [ ] 它们为什么能做到低停顿？
  答案：ZGC 和 Shenandoah 都是低延迟收集器，把标记、转移、重定位等大量工作并发化，使用读屏障/写屏障和染色指针等技术降低 STW 时间。 低停顿通常会付出额外 CPU、内存和吞吐成本。 ZGC 和 Shenandoah 都是低延迟收集器，目标是把大部分 GC 工作与用户线程并发执行，包括并发标记、并发转移/整理、并发引用处理等。它们通过读屏障或写屏障维护并发移动对象时的正确性，因此 STW 阶段很短，停顿通常更多和 GC Roots 扫描等阶段有关，而不是堆大小线性相关。 代价是它们需要额外 CPU、内存和屏障开销，吞吐可能低于吞吐优先收集器。低延迟系统选择它们之前，要确认业务是否真的需要极低 P99/P999 停顿，以及机器资源是否足够。 不是。低延迟收集器只是把 STW 时间压得很短，不代表完全没有暂停。比如初始标记、最终处理某些根集合、重映射阶段仍可能有短暂停顿。面试中要避免“无停顿 GC”这种绝对说法。 适合大堆、低延迟、对 P99/P999 停顿敏感的在线服务，比如交易、推荐、网关、搜索等。但如果业务是离线计算、批处理，更关注总吞吐，Parallel 或 G1 可能更合适。收集器选择要和延迟目标、堆大小、JDK 版本、CPU 资源一起评估。

## 17. 三色标记是什么？

- [ ] 并发标记为什么需要屏障？
  答案：三色标记把对象分为白、灰、黑。并发标记时用户线程还在修改引用，可能出现漏标，需要读/写屏障维护正确性。 CMS 常用增量更新，G1 常用 SATB 思想。 三色标记把对象分成白、灰、黑。白色表示尚未访问，灰色表示对象本身已访问但它引用的对象还没全部扫描，黑色表示对象和它的引用都扫描完成。并发标记时用户线程还在运行，引用关系可能变化，如果不处理，可能把仍然存活的对象漏标为白色，导致误回收。 为了解决并发修改问题，JVM 使用读屏障或写屏障记录引用变化。CMS 常用增量更新思想，关注黑对象新增对白对象的引用；G1 常用 SATB，关注标记开始时对象图的快照，把被删除的旧引用也记录下来，保证快照时存活的对象不被漏标。 SATB 是 Snapshot At The Beginning，即以标记开始时的对象图快照为准。并发标记期间，如果某个引用被覆盖，写屏障会把旧引用记录下来，避免这个旧引用指向的对象因为引用断开而被漏标。这样本轮可能多保留一些已经变成垃圾的对象，也就是浮动垃圾，但能保证正确性。 会。屏障是在对象引用读写路径上插入的额外逻辑，会带来 CPU 和内存开销。低停顿收集器的本质就是用更多并发工作和屏障成本，换取更短的 STW 停顿。

## 18. 什么是卡表和 Remembered Set？

- [ ] 为什么需要记录跨代/跨 Region 引用？
  答案：卡表把内存分成卡页，记录老年代到新生代等跨区域引用；RSet 记录其他 Region 指向当前 Region 的引用。这样 Minor GC 或 Region GC 不必扫描整个堆。 写屏障会维护这些结构，也会带来一定运行时开销。

## 19. GC 日志怎么看？

- [ ] 分析 GC 日志重点看哪些指标？
  答案：看 GC 类型、触发原因、回收前后各区域容量、停顿时间、Full GC 次数、晋升量、老年代增长、元空间、用户态/内核态时间。核心是判断是否频繁 GC、停顿是否超标、回收效果是否差。 只看平均值不够，要关注 P99 停顿和业务高峰期。 GC 日志分析先看全局：GC 频率、每次停顿时间、Full GC 次数、堆使用趋势、业务高峰是否对应 GC 抖动。再看分区：年轻代回收前后大小、老年代是否持续上涨、元空间是否增长、晋升量是否过大。然后看触发原因：Allocation Failure、Metadata GC Threshold、G1 Humongous Allocation、System.gc、to-space exhausted 等。 重点指标包括：Young GC 平均和 P99 停顿；Full GC 次数和最长停顿；每次 GC 后老年代占用是否下降；对象晋升速率；分配速率；GC 时间占比；是否频繁发生 promotion failed、concurrent mode failure、to-space exhausted；用户态/系统态时间是否异常。 可能说明老年代里大部分对象仍然被引用，存在内存泄漏或缓存过大；也可能是业务确实有大量长寿对象。下一步应该 dump 堆，使用 MAT、JProfiler、YourKit 等工具看 Dominator Tree、Retained Size 和 GC Roots 引用链，找出是谁持有这些对象。 先看分配速率是不是过高，是否有大量临时对象、JSON 解析、字符串拼接、大集合中间结果。再看年轻代大小是否太小、对象是否过早晋升。优化方向包括减少临时对象、复用缓冲、批量大小控制、调整年轻代比例或 G1 的年轻代目标，但优先看代码分配模式。

## 20. 频繁 Full GC 如何排查？

- [ ] 线上 Full GC 很频繁，你怎么定位？
  答案：先看 GC 日志确认触发原因，再看老年代、元空间、直接内存、晋升速率。用 heap dump 分析大对象和引用链，检查缓存、集合未清理、线程池队列、类加载泄漏、批处理大对象等。 不要一上来就加内存，先确认是内存泄漏、参数不合理还是流量突增。 第一步保留现场：确认告警时间、流量、版本变更、机器范围，打开或收集 GC 日志、应用日志、监控。第二步判断触发原因：是老年代满、元空间满、显式 GC、直接内存、晋升失败，还是 G1 humongous。第三步看 GC 效果：Full GC 后内存是否明显下降。如果下降明显，可能是流量峰值或参数不合理；如果下降不明显，更像泄漏或长寿对象过多。 第四步使用工具定位：`jstat` 看 GC 趋势，`jmap`/诊断命令导出 heap dump，MAT 看大对象和引用链，`jstack` 看线程和队列，必要时结合 async-profiler/JFR 看分配热点。第五步处理：如果是缓存无限增长，增加容量上限和过期策略；如果是 ThreadLocal 未清理，补 remove；如果是队列堆积，限流或降级；如果是大对象批处理，改分页或流式处理；如果是参数问题，再调整堆、年轻代、G1 目标等。 要谨慎。大堆 dump 会造成明显停顿和磁盘压力，可能把问题扩大。生产上要看服务重要性和高峰期，必要时先摘流量、在单台问题机器上 dump，或者使用 JFR、采样、历史 dump。OOM 时可以配置自动 dump，但也要保证磁盘空间。 加内存可能暂时降低 GC 频率，但如果是内存泄漏，只是把 OOM 推迟；如果堆更大，Full GC 停顿可能更长。正确做法是先判断是容量不足、参数不合理还是泄漏，再决定是否扩容。

## 21. 内存泄漏和内存溢出有什么区别？

- [ ] Java 有 GC 为什么还会内存泄漏？
  答案：内存泄漏是对象不再需要但仍被引用，导致不能回收；内存溢出是可用内存不足。Java 有 GC，但如果对象被静态集合、缓存、ThreadLocal、监听器等持有，仍会泄漏。 泄漏常表现为 Full GC 后内存仍持续上涨。

## 22. OOM 常见类型有哪些？

- [ ] 不同 OOM 分别怎么排查？
  答案：常见有 Java heap space、GC overhead limit exceeded、Metaspace、Direct buffer memory、unable to create new native thread。分别排查堆对象、GC 效率、类加载、直接内存、线程数量和系统资源。 OOM 时建议配置 `-XX:+HeapDumpOnOutOfMemoryError`。 `Java heap space` 表示堆放不下对象，重点看大对象、缓存、集合、查询结果、数据倾斜。`GC overhead limit exceeded` 表示 JVM 花大量时间 GC 却回收很少，通常堆接近耗尽。`Metaspace` 表示类元数据过多，常见于动态代理、频繁类加载、类加载器泄漏。`Direct buffer memory` 表示直接内存不足，常见于 Netty、NIO、堆外缓存。`unable to create new native thread` 表示线程创建失败，可能线程数过多或系统资源限制。还有 `OutOfMemoryError: Kill process or sacrifice child` 这类容器/操作系统层面的内存 kill，需要看 cgroup 和系统日志。 看异常类型和栈。堆 OOM 通常带 `Java heap space`；元空间是 `Metaspace`；直接内存是 `Direct buffer memory`；线程是 `unable to create new native thread`。如果是容器直接被 kill，Java 进程未必能打印 OOM，需要看 Kubernetes event、dmesg 或容器运行时日志。 看是否大量动态生成类，例如 CGLIB、Javassist、Groovy、表达式引擎、频繁热部署；看类加载器数量是否增长；用 `jcmd VM.classloader_stats`、JFR、MAT 分析类加载器引用链。解决方式包括复用类加载器、关闭无限动态生成、升级有泄漏的框架、设置合理 `MaxMetaspaceSize`。

## 23. JVM 调优常用参数有哪些？

- [ ] 生产常见 GC 参数怎么配？

## 24. 如何选择垃圾收集器？

- [ ] 高吞吐和低延迟场景怎么选？
  答案：后台批处理更关注吞吐，可选 Parallel；普通服务端默认 G1 是稳妥选择；超低延迟、大堆场景可考虑 ZGC/Shenandoah；小应用可用 Serial。最终要靠压测和 GC 日志验证。 收集器选择要结合 JDK 版本、堆大小、延迟目标、CPU 和业务峰值。

## 25. 一次完整 GC 调优怎么做？

- [ ] 你会按什么步骤调优？
  答案：先明确目标，如降低 P99 延迟或减少 Full GC；采集 GC 日志、监控和 dump；定位瓶颈，如晋升过快、老年代泄漏、元空间膨胀；调整代码或参数；压测验证；上线观察并保留回滚方案。 GC 调优最后往往是业务对象生命周期和内存使用方式的优化，不只是改 JVM 参数。 第一，明确目标。例如 P99 停顿从 800ms 降到 200ms，或者 Full GC 每小时 5 次降到 0。第二，采集证据，包括 GC 日志、堆使用曲线、分配速率、线程数、QPS、RT、错误率、dump、JFR。第三，定位主要矛盾：是分配太快、年轻代太小、晋升过快、老年代泄漏、元空间膨胀、直接内存不足，还是收集器不适配。第四，先改业务对象生命周期，再调 JVM 参数。第五，压测验证，不只看平均值，要看 P95/P99、吞吐、CPU、内存和错误率。第六，灰度上线并保留回滚。 比如接口 P99 抖动，GC 日志显示 Young GC 每几秒一次，晋升量很大，老年代持续上涨。Heap dump 发现每次请求把几万条数据一次性查出并构造成大 List，接口结束前还被日志上下文引用。优化方式是分页查询、流式处理、减少中间对象、及时清理上下文。参数上适当增大年轻代或调整 G1 目标只是辅助，核心是降低对象分配和存活时间。 GC 回收的是应用创建出来的对象。如果业务代码持续制造大量临时对象、无限缓存、超大集合、未清理 ThreadLocal，再怎么调参数也只能缓解。真正稳定的优化通常来自减少分配、缩短对象生命周期、控制缓存边界、消除泄漏和改善数据处理方式。
